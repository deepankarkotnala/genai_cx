Deep Dives / Agent Protocols — MCP · A2A · A2UI

1 · What you already know

From module 09 you know MCP: a host, a client per server, and three primitives, with the tool description arriving as text you did not write. From module 13 you know a supervisor delegating to workers inside your own process.

This page is about the boundaries those two stop at. A worker that belongs to another company is not a function call, and a person is not a text stream.

2 · What breaks now

The same integration problem appears three times, at three different boundaries.

Boundary one, the tool. Four applications each need the ticket system, so four teams write four integrations:

4 apps x 5 tools, hand-written = 20 integrations to maintain

Boundary two, the peer. Your agent must hand a task to a fraud-review agent owned by another team, running a framework you do not use, taking up to two hours:

result = fraud_agent(case)     # a function call cannot express "come back in an hour"

Boundary three, the person. The agent needs a date, a seat preference and a currency. Asked in prose, users mistype them; generated as front-end code, the model's output is executable in your page.

BoundaryWhat a plain function call cannot express
A capability another app also needsDiscovery, so the caller learns what exists at run time
An agent you do not controlA task that outlives the request, and a peer that may refuse
A person who needs a widgetStructure a client can render with its own components

All three are the same shape. A function call assumes the far side is inside your process, returns immediately, and cannot decline.

3 · Simple breakdown — MCP vs A2A (and where A2UI fits)

A MCP — the tool boundary

What it is. MCP is an open protocol for exposing tools, read-only resources and prompt templates to a model application over JSON-RPC.

Core purpose. It lets one team maintain a capability once, so every compliant host can use it without writing its own integration.

Execution model.

Architecture under the hood. A host running the model, one client per connected server, and servers that each wrap one system and hold its credentials.

State handling. The unit of work is a single tool call: arguments in, content out. Nothing about the call persists in the protocol.

Limitations and advanced features. Every connected tool costs prompt tokens on every call. Descriptions come from the server, so they are text you did not write. Remote transports need authentication you configure.

B A2A — the peer boundary

What it is. A2A is an open protocol for one agent to delegate work to another agent, which may belong to a different team or a different company.

Core purpose. It crosses a boundary you do not control, and models work that may take minutes or hours rather than returning immediately.

Execution model. The client sends a message and receives a Task: an object with a lifecycle, artifacts, and states including one for needing more input.

Architecture under the hood. An agent card for discovery, a task store, and mutual authentication because neither side is in charge.

State handling. The task is durable and addressable, so it can be polled, resumed after INPUT_REQUIRED, or cancelled.

Limitations and advanced features. Higher latency and more moving parts. The far side is a black box that can refuse, so you must handle a peer that declines or never finishes.

The core differences

MCP — the tool boundaryA2A — the peer boundaryA2UI — the human boundary
The counterparty isA capability, with a visible schemaAn agent with its own goals, opaque to youA client that renders components
Unit of workOne tool call, returns a valueA Task with a lifecycleA UI surface and its updates
Can the far side refuseIt can errorYes, it can declineIt renders or it does not

In short — which one to choose

  • Reach for MCP first. The tool boundary is the one you hit soonest, and it is where duplicated integrations actually cost you.
  • Reach for A2A when the far side is another organisation, or the work is long-running enough to need a task lifecycle.
  • Reach for A2UI when text-only interaction is measurably costing completion rate, and you want your own components rather than model-generated code.
  • Skip all three for one app, one team, a handful of in-process tools. A protocol with no boundary to cross is pure overhead.

4 · Without the technology

Without protocols you write a bespoke adapter per pair. Here is the peer boundary, done by hand:

import requests, time

def fraud_review(case):
    started = requests.post(FRAUD_URL, json={"case": case}).json()   # their shape
    job_id = started["reviewId"]                                      # their field name

    while True:                                    # you invented this polling contract
        time.sleep(30)
        status = requests.get(f"{FRAUD_URL}/{job_id}").json()
        if status["state"] == "done":
            return status["outcome"]
        if status["state"] == "needs_info":
            return {"error": "cannot supply more info"}   # no protocol for resuming
        if time.time() - start > 7200:
            return {"error": "gave up"}                    # no cancel, either

This works, and it is what most teams ship first. What it does not give you:

  • A shared vocabulary. Their reviewId and state are theirs. The next vendor names them differently, and you write this again.
  • A resume path. When the peer needs more input there is nowhere to put the answer.
  • Cancellation. You can stop waiting; you cannot stop their work.
  • Discovery. What else can that agent do? You read their documentation, if it exists.

A2A is that adapter, standardised, with the lifecycle states written down. The protocol is not cleverer than your code; it is the same code that everyone agreed on.

5 · Runtime mechanics

One A2A delegation, in order:

  1. The client fetches the peer's agent card and learns its skills and authentication schemes.
  2. It authenticates, mutually — neither side is in charge, so both prove who they are.
  3. It sends a message, and receives a Task rather than a value.
  4. The task moves through states: submitted, working, and possibly INPUT_REQUIRED.
  5. Either the client polls with GetTask, or the peer calls a webhook the client registered.
  6. The task reaches completed, failed or cancelled, carrying artifacts.

Step 3 is the whole difference from MCP. A tool call returns a value; a task is an object you can come back to, which is what makes two-hour work expressible.

6 · Smallest working version

import requests

# 1 - discovery: what can this agent do, and how do I authenticate?
card = requests.get("https://fraud.example.com/.well-known/agent-card.json").json()
# {'name': 'fraud-review', 'skills': ['review a disputed charge'],
#  'authentication': {'schemes': ['oauth2']}, 'endpoint': '...'}

# 2 - send work, receive a Task rather than an answer
task = requests.post(card["endpoint"], json={
    "message": {"role": "user", "parts": [{"text": "Review case C-4821."}]},
}, headers=auth).json()
# {'id': 'task_9f2c', 'state': 'submitted'}

# 3 - register a webhook, rather than holding a connection open for two hours
requests.post(f"{card['endpoint']}/tasks/{task['id']}/pushNotification",
              json={"url": "https://us.example.com/hooks/fraud"}, headers=auth)

# 4 - the peer may need something before it can finish
#     state INPUT_REQUIRED, and you resume the same task by id
requests.post(card["endpoint"], json={
    "taskId": task["id"],
    "message": {"role": "user", "parts": [{"text": "Cardholder confirmed by phone."}]},
}, headers=auth)

The task id is the whole mechanism. It survives the request, so the work can pause for input and resume without either side holding a connection.

7 · The components, one at a time

The agent card

Discovery for peers, as tools/list is discovery for tools. It names skills and authentication schemes at a well-known URL.

The Task

submitted -> working -> completed
                     -> input-required -> working -> completed
                     -> failed
                     -> canceled

input-required is the state a function call cannot express, and the reason A2A exists rather than a REST endpoint.

Push notifications

# webhooks retry, so the handler must be idempotent
def on_task_update(payload):
    if ledger.seen(payload["taskId"], payload["state"]):
        return 200
    ledger.record(payload["taskId"], payload["state"])
    advance(payload)

A webhook that is not idempotent will double-process, because retries are part of the delivery contract rather than an error.

A2UI, in one paragraph

The agent emits declarative JSON naming components from a catalog the client already holds. The client renders them with its own widgets.

{"createSurface": {"catalogId": "checkout-v3", "surfaceId": "s1"}}
{"updateComponents": {"surfaceId": "s1",
                      "components": [{"type": "DatePicker", "id": "d1",
                                      "label": "Delivery date"}]}}

The agent can only request components that already exist, so there is no arbitrary code execution and the result inherits the host application's styling. The alternative — the model writing front-end code into an iframe — ships model output as executable code.

What none of them moves

Validation, authorisation and approval stay in your host. A protocol standardises how the far side is described and reached, never whether calling it is safe.

The middleware that enforces that — identity propagation, argument-level authorisation, tenant isolation and the confused-deputy rule — is set out in Middleware, Identity and Agent Interoperability. A protocol moves the boundary; it moves none of those checks.

8 · State and data flow

  1. What data is state? For MCP, the session's negotiated capabilities. For A2A, the Task. For A2UI, the surface and its components.
  2. Who writes each field? MCP: both sides at initialisation. A2A: the peer owns the task state; you own the message you send.
  3. Who reads each field? Your host reads all three, and only your host decides what to do about them.
  4. Replaced, appended or merged? A task's state is replaced as it advances; its artifacts accumulate.
  5. What reducer controls merging? None in the protocol. Your code decides how an artifact merges into your own state.
  6. Is it only in process memory? An MCP session, yes. An A2A task, no — that is the point of it.
  7. Is it checkpointed? The task is durable at the peer, and addressable by id.
  8. Is it in a database? The peer's task store, and your own record of the task ids you are waiting on.
  9. How long does it survive? An MCP session lasts the connection. A task lasts until it reaches a terminal state.
  10. What thread, user or key retrieves it again? The task id, which you must persist. Losing it means losing work that is still running.

Rows 6 and 10 together are the practical warning. An MCP session dropping means re-initialising; an A2A task id lost means work continues that nobody is waiting for.

9 · Full code, in assembly order

import json, hashlib

# 1 - MCP: connect, then verify nothing changed since review
mcp = MCPClient(["python", "tickets_server.py"])
for tool in mcp.call("tools/list")["tools"]:
    fingerprint = hashlib.sha256(
        f"{tool['name']}|{tool['description']}|"
        f"{json.dumps(tool['inputSchema'], sort_keys=True)}".encode()).hexdigest()[:16]
    if fingerprint != APPROVED[tool["name"]]:
        raise RuntimeError(f"{tool['name']} changed since review")   # module 09

# 2 - namespace, so two servers cannot shadow one another
tools = {f"tickets__{t['name']}": remote(mcp, t["name"]) for t in mcp.call("tools/list")["tools"]}

# 3 - A2A: a peer is not a tool, so it gets its own path
def delegate_fraud(case_id, caller):
    task = a2a.send(FRAUD_CARD, f"Review case {case_id}", auth_for(caller))
    pending.record(task["id"], case_id, caller)      # persist the id, or lose the work
    return {"status": "delegated", "task_id": task["id"]}

# 4 - the webhook resumes the run, and must tolerate retries
def on_fraud_update(payload):
    if ledger.seen(payload["taskId"], payload["state"]):
        return 200                                    # already processed
    ledger.record(payload["taskId"], payload["state"])
    if payload["state"] == "input-required":
        a2a.send(FRAUD_CARD, extra_info_for(payload), task_id=payload["taskId"])
    elif payload["state"] == "completed":
        resume_run(pending.get(payload["taskId"]), payload["artifacts"])

# 5 - A2UI: ask the person with components, not prose
def ask_for_date(surface):
    return {"updateComponents": {"surfaceId": surface,
                                 "components": [{"type": "DatePicker", "id": "d1",
                                                 "label": "Delivery date"}]}}

# 6 - the host still owns every check, unchanged from modules 03, 08 and 09
answer = run(goal, {**LOCAL_TOOLS, **tools, "delegate_fraud": delegate_fraud},

10 · Trace

One request that crosses all three boundaries:

run-6b3d  handle dispute C-4821
  t+0.00  tickets__read_ticket        MCP    41 ms    -> ticket, order ORD-5581
  t+0.05  delegate_fraud              A2A   180 ms    -> task_9f2c, state submitted
  t+0.24  ask_for_date                A2UI    2 ms    -> DatePicker rendered
          [run ends here; nothing is held open]

  ... 14 minutes later, the peer needs something ...

  t+14m   webhook  task_9f2c  state=input-required
  t+14m   a2a.send task_9f2c  "cardholder confirmed by phone"

  ... 51 minutes later ...

  t+65m   webhook  task_9f2c  state=completed, artifacts=[verdict.json]
  t+65m   resume_run(C-4821)  -> refund approved, pending human approval

Read the line marked run ends here. No process waited 65 minutes. The task id was persisted, the request returned, and a webhook resumed the work — which is exactly what a function call cannot do.

11 · Break it

Treat the peer as a tool. It is the natural first attempt, because it is one line shorter:

def delegate_fraud(case_id):
    return a2a.send_and_wait(FRAUD_CARD, f"Review case {case_id}", timeout=30)

t+0.0   delegate_fraud(case_id='C-4821')
t+30.0  TimeoutError
        -> the agent reports "fraud review failed"
        -> the task is still running at the peer
        -> nobody is waiting for it, and nothing records that it exists

t+65m   the peer completes the review and calls a webhook nobody registered

The work succeeded and the answer was thrown away. Worse, the agent told the customer the review failed, and a retry starts a second review of the same case, because no task id was persisted to recognise the first.

12 · Fix it

1 · Return the task, not the answer. The delegation ends when the task is accepted:

task = a2a.send(FRAUD_CARD, f"Review case {case_id}", auth)
pending.record(task["id"], case_id, caller)       # persist before returning
return {"status": "delegated", "task_id": task["id"]}

2 · Register a webhook rather than holding a connection. A 65-minute HTTP request will be killed by something in the path regardless.

3 · Make the handler idempotent, because webhook retries are part of the contract:

if ledger.seen(payload["taskId"], payload["state"]):
    return 200

4 · Handle input-required as a normal state, not a failure. It is the state that distinguishes a peer from a tool, and treating it as an error throws away work that is nearly finished.

5 · Verify the peer's claims. A completed task's artifacts came from a system you do not control. Validate them exactly as you validate a tool result from module 03.

15 · Interview preparation

🎤
Q · "What's the difference between MCP and A2A?"

"Different boundaries. MCP standardises how an agent uses capabilities — tools, resources, prompts — over JSON-RPC, where the counterparty is transparent and I can see the schemas. A2A standardises how an agent delegates to another agent, which is a black box, possibly at another company. The tell is the unit of work: MCP's is a tool call, A2A's is a Task with a lifecycle, artifacts, and interrupted states for when the remote agent needs input or auth. They compose — an A2A remote agent typically uses MCP internally."

🎤
Q · "Why not just have the model generate the UI as code?"

"Two reasons, security and consistency. Generated code is executable model output — an injection and exfiltration surface, and if you sandbox it in an iframe it looks nothing like the rest of the product. A2UI keeps the payload declarative: the agent names components from a catalog the client already trusts, and the client renders them with its own widgets. Safe like data, expressive like code. It also stays machine-readable, so an orchestrating agent can tell what's on screen — which generated HTML in an iframe cannot."

🎤
Q · "How would you handle an agent task that takes two hours?"

"A2A models it directly. SendMessage returns a Task rather than a value, so I'd register a push-notification config — a webhook — instead of holding a streaming connection open, and make the handler idempotent because webhooks retry. The client can also GetTask to poll, and CancelTask if the user backs out. If the remote agent needs something mid-flight it moves the task to INPUT_REQUIRED and I resume it, rather than the whole thing failing."

🎤
Q · "What changed in MCP recently?"

"The 2026-07-28 revision made it stateless at the protocol layer — the initialize handshake and Mcp-Session-Id header are gone, with client metadata in _meta per request. That's an operations win: no sticky routing or shared session store, so any instance serves any request. It also formalised Extensions with reverse-DNS IDs, shipped MCP Apps and Tasks as official extensions, hardened authorization, and deprecated Roots, Sampling and Logging under a 12-month policy. Tools, resources and prompts didn't change."

🎤
Q · "Would you adopt all three?"

"Only where there's a boundary to justify it. MCP first — the tool boundary shows up in every project and a governed capability layer pays for itself. A2A once a second organisation or a long-running delegation appears; before that its ceremony buys nothing. A2UI when I can show text-only interaction is costing completion rate. For a single-team chatbot with five in-process tools, direct function calling is the right answer and I'd say so."

16 · In short, and what comes next

Remember these six:

  • Each protocol names one boundary: MCP a capability, A2A a peer, A2UI a person.
  • A tool call returns a value; an A2A task is an object you can come back to.
  • input-required is the state a function call cannot express.
  • Persist the task id before returning, or work runs that nobody is waiting for.
  • Webhook retries are the contract, so the handler must be idempotent.
  • No boundary means no protocol. For one app and one team, call the function.
🔑
The one idea to remember

A protocol standardises how the far side is described and reached, never whether calling it is safe. Validation, authorisation and approval stay in your host, exactly where modules 03, 08 and 09 put them.
