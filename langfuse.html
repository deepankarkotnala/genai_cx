Production / Langfuse — LLM observability

1 · What you already know

From the tracing page in the agent section: a run id on every span, a parent id to nest them, and token counts captured at the call. From the evaluation page: a golden set that gates a release.

This page is what those look like when a tool holds them, and what the tool adds that a log file cannot.

2 · What breaks now

You have logging with a run id, so you can reconstruct one request. A user reports a bad answer, and four questions follow:

The questionWhat the logs can answer
What did this request do?Everything, if you filter by the run id
Where did the 4 seconds go?By subtracting timestamps, if the lines are the right ones
Was the answer any good?Nothing. There is nowhere to record that
How many requests were like this one?Nothing. Each line is independent

The first two are a structure problem, and a correlation id mostly solves them. The last two are a different kind of gap.

A log line records that something happened. It has no field for whether it was correct, because correctness is decided later — by a user clicking thumbs-down, by a rule checking a citation, or by a judge scoring faithfulness. Quality arrives after the request has finished, and a log line is already written.

3 · Simple breakdown — a tracing platform vs your own logging

A Langfuse

What it is. Langfuse is an open-source platform that records each request as a trace of nested spans, attaches quality scores to them, and stores prompts and evaluation datasets alongside.

Core purpose. It answers what one request did, what it cost, and whether it was any good, without you building a trace store and a viewer.

Execution model.

Architecture under the hood. An SDK that wraps your calls, a server that ingests spans asynchronously, and a database holding traces, scores, prompts and datasets.

State handling. Traces and scores are durable and queryable. A session groups a conversation; a user id groups everything one person did.

Limitations and advanced features. The SDK batches and flushes in the background, so a process that exits without flushing loses the trace. Traces hold prompts and completions, so retention is a data-protection decision rather than a storage one.

B Your own logging

What it is. Log lines written at each call site, usually at a severity level, with whatever fields the caller included.

Core purpose. It records that something happened, with no dependency and no new service to run.

Execution model. Each call site writes a line when it is reached. Nothing relates one line to another unless a field does.

Architecture under the hood. A logger and a sink. No structure beyond what each line carries.

State handling. Whatever each line holds. There is no request-level object and no score.

Limitations and advanced features. Reconstructing one request means filtering and guessing. Durations must be subtracted by hand, and there is nowhere to attach a quality score.

The core differences

LangfuseYour own logging
Reassembles one requestYes, by trace and parentOnly if every line carries a correlation id
Attaches a quality scoreYes, that is the pointNo
Operational costA service to run, or a hosted planAlmost none

In short — which one to choose

  • Use a tracing platform once you need to answer why a request was slow, dear or wrong — which is roughly when real users arrive.
  • Use your own logging before that, and put a run id on every line so the traces you add later can find them.
  • The important part is neither tool. It is deciding that a request is the unit you record, and that quality is a number attached to it.

4 · Without the technology

You can build this yourself, and the first version is genuinely small:

import json, time, uuid

def traced(fn):
    def wrapper(*args, run_id=None, **kwargs):
        span = {"id": uuid.uuid4().hex[:8], "run_id": run_id,
                "name": fn.__name__, "started": time.time()}
        try:
            return fn(*args, **kwargs)
        finally:
            span["duration_ms"] = int((time.time() - span["started"]) * 1000)
            db.insert("spans", span)
    return wrapper

That gives you nested timing. What it does not give you, and what each one costs to add:

  • A viewer. A trace is a tree, and reading trees in a database is what the tool is mostly for.
  • Scores attached after the fact. A thumbs-down arrives minutes later and must find its trace.
  • Aggregation. "How many requests scored below 0.5 this week" is a query you now own.
  • Asynchronous flushing. That db.insert is on the request path, so tracing now costs latency.

The fourth is the one that bites first. Naive instrumentation makes every request slower in order to record how slow it was.

5 · Runtime mechanics

One traced request, in order:

  1. A trace is opened when the request arrives, carrying a user id and a session id.
  2. Each unit of work opens a span, and a model call opens a generation, which also records model, tokens and cost.
  3. Spans close as work finishes, and are buffered in memory rather than written immediately.
  4. A background flush sends the batch to the server, off the request path.
  5. Scores attach to the trace afterwards — from a user, a rule, or a judge running on a sample.

Step 5 is what separates this from logging. The record stays open to being scored after the request is over, which is exactly when quality becomes knowable.

6 · Smallest working version

from langfuse import observe, get_client

@observe()                                  # this function becomes a span
def retrieve(question):
    return search_kb(question)

@observe(as_type="generation")              # a generation records tokens and cost
def answer(question, hits):
    return model(build_prompt(question, hits))

@observe()                                  # the outermost call becomes the trace
def handle(question, user_id, session_id):
    client = get_client()
    client.update_current_trace(user_id=user_id, session_id=session_id)

    hits = retrieve(question)
    reply = answer(question, hits)

    # a deterministic score, recorded at request time
    client.score_current_trace(
        name="has_citation",
        value=1 if any(h["id"] in reply for h in hits) else 0)
    return reply

Three decorators. The tree, the token counts and the cost come from the SDK, and the only thing you wrote is the one score that a rule can decide.

7 · The components, one at a time

The five objects

ObjectWhat it is
TraceOne end-to-end request. The container everything else hangs from
SpanA unit of work inside it, with a start and an end. Spans nest
GenerationA span for a model call, also recording model, tokens and cost
ScoreA quality measurement attached to a trace or a generation
Session and userGrouping: a conversation, and everything one person did

Learn those five and the rest of the product is detail.

Three sources of scores

user feedback   thumbs up or down, a rating          # the signal that matters most
programmatic    did it cite? is it valid JSON?       # cheap, deterministic, at request time
judge           faithfulness against a rubric        # scales without people, and can be wrong

Record all three under different names, so a disagreement between the judge and the users is visible rather than averaged away.

Sessions and users

client.update_current_trace(user_id="alice", session_id="chat_42")

Without these, a trace is an orphan. With them, "show me every request in the conversation that ended in an escalation" is one query.

Prompt management

prompt = client.get_prompt("support-system", label="production")
reply = model(prompt.compile(question=question))

The prompt is versioned in the platform and linked to the traces that used it, which is the attribution the LLMOps page insisted on. The risk is that editing a prompt outside version control is a change nobody reviewed.

Datasets and offline runs

The golden set from the evaluation page, stored next to the traces, so a run against a new prompt version compares directly with production behaviour.

The flush

client.flush()          # before a short-lived process exits

The SDK batches in the background. A script or a serverless function that exits without flushing loses its traces, which is exactly the run you wanted.

8 · State and data flow

  1. What data is state? The open trace and its spans, plus buffered spans not yet sent.
  2. Who writes each field? The SDK, as work starts and finishes; your code, for scores and metadata.
  3. Who reads each field? You, afterwards. Nothing in the request reads its own trace.
  4. Replaced, appended or merged? Spans append. A score is a new record rather than an edit.
  5. What reducer controls merging? None. The parent id defines the tree at read time.
  6. Is it only in process memory? Only until the flush, which is why the flush matters.
  7. Is it checkpointed? Flushing per batch is the equivalent. A crash loses whatever is still buffered.
  8. Is it in a database? Yes, and it holds prompts and completions.
  9. How long does it survive? Your retention setting. This is a data-protection decision.
  10. What thread, user or key retrieves it again? The trace id, the session id, or the user id.

Rows 6 and 8 are the two that cause production surprises. An unflushed trace is lost, and a retained trace is personal data — and both are decided by a default until somebody changes it.

9 · Full code, in assembly order

import os
from langfuse import observe, get_client

os.environ["LANGFUSE_PUBLIC_KEY"] = ...        # never hard-coded
os.environ["LANGFUSE_SECRET_KEY"] = ...

@observe()
def retrieve(question):
    hits = search_kb(question)
    get_client().update_current_observation(
        metadata={"hit_count": len(hits),
                  "top_score": hits[0]["score"] if hits else None})
    return hits

@observe(as_type="generation")
def answer(question, hits):
    prompt = get_client().get_prompt("support-system", label="production")
    return model(prompt.compile(question=question, context=hits))

@observe()
def handle(question, caller):
    client = get_client()
    client.update_current_trace(user_id=caller.id, session_id=caller.session,
                                tags=["support", caller.tenant])

    hits = retrieve(question)
    reply = answer(question, hits)

    # 1 - deterministic scores now, while the facts are to hand
    client.score_current_trace(name="has_citation",
                               value=1 if cited_ids(reply) else 0)
    client.score_current_trace(name="refused",
                               value=1 if reply.strip() == "NOT_IN_CONTEXT" else 0)
    return reply

# 2 - a user score arrives later, and finds its trace by id
def on_feedback(trace_id, helpful):
    get_client().create_score(trace_id=trace_id, name="user_helpful",
                              value=1 if helpful else 0)

# 3 - short-lived processes must flush, or the trace is lost
get_client().flush()

11 · Break it

Instrument a batch job the obvious way, and run it:

for ticket in tickets:            # 500 tickets
    handle(ticket.question, ticket.caller)
print("done")                     # process exits here

expected traces:  500
traces in Langfuse: 487

Thirteen traces are missing, and they are the last thirteen. The SDK batches in the background, the process exited before the final batch was sent, and nothing raised.

Then a second problem, found by someone else:

TRACE support-qa
  |- SPAN retrieve   input: "my card ending 4412, DOB 1988-03-02, refund please"

The trace store now holds card fragments and dates of birth, because the default is to capture inputs and outputs verbatim and nobody changed it.

12 · Fix it

1 · Flush before the process exits. One line, and it is the whole of the first bug:

get_client().flush()             # or use the SDK context manager

The same applies to serverless handlers, which can be frozen the instant they return.

2 · Mask at capture, not in the viewer. A value redacted downstream was still written upstream:

Langfuse(mask=lambda data: redact_pii(data))     # applied before anything is sent

3 · Record shape rather than payload where the content is not needed:

metadata={"hit_count": 3, "chars": 1840}         # not the documents themselves

Masking is the same control the guardrail layer applies to a reply — see the output screen, and RAG production concerns for what a retrieval trace holds.

4 · Set a retention period deliberately. Traces hold conversations, so the default is a decision somebody should make on purpose.

5 · Sample the expensive parts, keep all the interesting ones. Judge scores on a sample; every error and every high-cost run retained in full.

15 · Interview preparation

Beginner What are the core objects in Langfuse? ›

Five. A trace is one end-to-end request. A span is a unit of work inside it. A generation is a span for a model call, also recording model, tokens and cost. A score is a quality measurement attached to a trace. Sessions and users group traces.

Beginner What does a score give you that a log line does not? ›

Somewhere to record whether the answer was any good. Quality is decided after the request finishes — by a user, a rule or a judge — and a log line is already written by then.

Intermediate Where do scores come from? ›

Three places. User feedback, which is the signal that matters most. Programmatic checks that are cheap and deterministic, such as whether a citation is present. And a judge model scoring against a rubric, which scales without people and can be wrong. Keep them under separate names so disagreement is visible.

Intermediate Why does instrumentation have to be asynchronous? ›

Because writing a span synchronously puts storage latency on the request path, so every request gets slower in order to record how slow it was. The SDK buffers and flushes in the background, which is also why a process that exits without flushing loses its last batch.

Senior A batch job produced 500 results but only 487 traces. What happened? ›

The process exited before the final batch was flushed. The SDK batches in the background and nothing raises when the buffer is discarded at exit. Call flush before the process ends, and the same applies to serverless handlers, which can be frozen the moment they return.

Senior What is the data-protection risk in a tracing platform? ›

Traces capture inputs and outputs verbatim by default, so a customer pasting a card number or a date of birth puts it in the trace store. Mask at capture rather than in the viewer, because a value redacted downstream was still written upstream. Then set a retention period deliberately instead of accepting the default.

Staff · design How would you use tracing and scoring together to improve a RAG application? ›

Score every request programmatically on things a rule can decide — citation present, refusal, schema valid — and attach user feedback when it arrives. Sample a judge for faithfulness. Then look for the disagreements: high judge scores with thumbs-down means the rubric measures the wrong thing; low citation rate with high satisfaction means the citation rule is too strict. Feed every confirmed failure into the golden set, so the offline suite gains a case for each real-world failure mode.

16 · In short, and what comes next

Remember these six:

  • Five objects: trace, span, generation, score, session. The rest is detail.
  • A score is what a log line cannot hold, because quality is decided after the request.
  • Record user, rule and judge scores separately, so disagreement stays visible.
  • Flush before a short-lived process exits, or you lose the last batch.
  • Mask at capture. A trace store holds conversations, so retention is a policy decision.
  • Fetch prompts by label, so every trace records which version produced it.
🔑
The one idea to remember

Tracing tells you what happened; a score tells you whether it was any good. The second one has to arrive late, and that is the whole reason a trace is a record you can add to rather than a line you already wrote.
